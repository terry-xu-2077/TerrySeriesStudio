# Word 式剧本／分镜批注与修订体验

> 日期：2026-10-20 · 状态：产品交互基线（尚未开发）

## 设计原则

**剧集工作室首先是带 AI 的文档编辑器。** 用户无需理解 Agent、审查轮次、任务对象、运行历史或数据结构。打开剧本，直接编辑；选择文字，写批注；AI 审查后，逐条接受或忽略建议。设计体验参照 Word 的「批注」与「修订」，但不追求实现完整 Word 格式系统。

同一交互模型用于**剧本**和**分镜脚本**：剧本是文档正文；分镜可为表格/镜头卡，但点击一个镜头的文本仍可原位选中、批注、修订。ShotMill 的 [Terry分镜表分支](https://github.com/terry-xu-2077/TerryShotMill/tree/codex/storyboard-sheet-ui-20261020) 是既有 UI 与文本编辑能力的主要参考。

## 当前交互原型

已建立可独立打开的 [demo/index.html](../demo/index.html) 和 [使用说明](../demo/README.md)。原型包含文字编辑、选区浮动「添加批改」、右侧常驻审查结果与原文关系连线、模拟 AI 审查、独立顶栏「批准本稿」、接受/忽略、保存/撤销等交互；AI 与评论数据模拟，未接正式 API 或工程文件。本文件继续作为正式实现的交互基线。

## 核心交互（V1 只做这些）

1. **直接写**：像文字处理软件一样点击正文输入，保持自动保存和 Ctrl+Z / Ctrl+Y。正常编辑不要求切换特殊「审核模式」。
2. **选中文本 → 批改**：只出现一个轻量浮动按钮「添加批改」，点击后在所选文字附近显示**输入批改的小浮窗**，填写完成后保存并在右侧批改结果栏新增卡片；不在常驻工具栏并排放「批注」「AI 审查」。
3. **AI 审查结果**：在右侧审查栏触发「AI 审查全文」后，返回的批注卡片**常驻正文右侧**，而不是浮窗。每条批注与对应文字用柔和关系线相连，点击卡片定位并高亮原文；滚动、调整窗口时重新计算连线，无法精确定位的意见放入摘要，不伪造关系线。
4. **接受 / 忽略建议**：AI 的建议改写是独立的 `suggestion`，接受才修改正文，忽略则保留。人工批注无需强行附带替换稿，可标记已处理。所有操作可撤销；**AI 不直接改写人工正在编辑或已批准的正文**。
5. **AI 自动批改循环**：后台最多按项目设置轮数进行「写作 → 审查 → 候选修订 → 复审」，但修订发生在**候选版本**上，不覆盖当前正在编辑的文档。循环结束默认只展示候选修订与对应问题，用户可逐条接受建议或主动切换查看整体候选稿；用户点击「批准本稿」才将批准快照交给下一阶段。
6. **分层明确**：顶部正中央只有一组「剧本 / 分镜 / 生成」工作区切换，不在左侧重复出现；左侧项目侧栏仅显示项目与剧集。右侧批改结果栏可以收起，但已有意见在桌面端随文档常驻并留有与原文相连的关系线。只有「添加批改」输入采用选区浮窗；**「批准本稿」独立位于页面顶部定稿区**，绝不与批改操作并排。

## 一条真实操作路线

打开 EP01 剧本 → 直接修改对白 → 选中一句话 → 点击浮动「添加批改」→ 在就近弹出的输入框填写意见 → 批改意见出现在右侧并由线连接到这句正文 → 需要 AI 审稿时在右侧点击「AI 审查全文」→ 对右侧卡片逐条「接受」或「忽略」→ 在页面顶栏独立点击「批准本稿」。

在分镜表内同样操作：选中某个镜头的动作描述，批注「动作接不上上一镜」；AI 定向改写该镜头，不因此重写全张分镜表或改变已批准资产。

## 表现与边界

- **默认专注写作**：项目导航默认收起，正文是视觉中心；右侧批改结果无内容时可以保持隐藏，有有效批改意见后桌面端固定显示在右侧。选择文字才出现局部批改输入浮窗。提供「展开项目导航 / 专注写作」切换。
- 正文始终是主区域；右侧批改卡片在独立固定栏中展示，关系线与正文的唯一文本锚点相连。正文或右侧卡片滚动时更新线条，原文已经改动或无法定位时隐藏关系线并提示失效，绝不连到相似文字。窄屏使用右侧抽屉且隐藏跨屏连线。
- 一眼能区分**人工批注**、**AI 批注**和**待接受修订**，但不堆叠大量彩色状态。
- 逐条接受建议只替换对应文字，不更改无关段落、对白、其他批注或媒体引用。
- 同一段文字被修改／删除，原批注不得悄悄定位到另一段相似内容：按稳定块 ID + 文本锚点及内容校验，不能确定时标记「引用位置已失效」供手动重新关联。
- 保存保持可读的普通工程文件：`script.md` 为剧本文本；`script.review.json` 保存批注、锚点、候选文本与处理状态；批准版本有独立快照。分镜使用已有结构化 JSON 的镜头 ID + 文本字段路径关联批注，无须数据库。
- 用户编辑期间若 AI 的异步审查结果返回，应先核对输入文档版本。版本不一致时标记「基于旧稿的建议」，不覆盖或强行套用现有文字。
- 批注中的「AI 修订」不等于自动批准；没有用户明确批准的正式稿，不进入下一个生产阶段。

## 两份审查 Skill 与统一批注协议

- [剧本批改 Skill](../skills/script-review/SKILL.md)：负责人物、冲突、对白、因果、节奏和剧情一致性等**审查标准**。
- [分镜批改 Skill](../skills/storyboard-review/SKILL.md)：负责镜头目的、空间/动作连续性、节奏和**生成可行性**等审查标准。
- [Terry Review v1 结构与校验](../src/review/schema.ts)：应用唯一的 AI 输出协议，提供 `REVIEW_RESPONSE_JSON_SCHEMA`、`parseReviewResponse` 和 `anchorReviewComments`。Skill 不复制协议的字段定义。

**API 提交**：应用把本次审查文本按稳定 `block_id` 组成块列表，附上原始 `document_revision`、当前剧集目标和相关设定。调用时装载选定 Skill 的内容 + 统一 JSON Schema。无论云端模型支持严格结构化输出与否，**应用都必须再次校验实际响应**。

典型返回（示例，不代表已接入 API）：

```json
{
  "format": "terry-review",
  "version": 1,
  "document_revision": "ep01-script-rev3",
  "comments": [
    {
      "block_id": "scene03-dialogue04",
      "quote": "我们没有别的选择了。",
      "comment": "这句话过于抽象，可用眼前的生存困境让人物更具体。",
      "replacement": "不这么做，明天我们连水都没有。",
      "severity": "suggestion"
    }
  ]
}
```

**定位规则**：先核对文档修订号，再在对应 `block_id` 的原文里做**精确且唯一**的 `quote` 匹配，程序计算 UTF-16 选区。旧版本、原文已变、引用重复或块不存在时都不能自动挂到相似文字上；应显示未定位批注供用户查看。

**文本保存**：`script.md` 存剧本文字；`script.review.json` 计划存评论 ID、作者、处理状态、锚点与修订号。分镜 JSON 则通过镜头稳定 ID + 字段路径生成 `block_id`。Markdown 解析时须为文档块维护稳定标识映射，不能用会随插删改变的「第 3 段」当 ID。文件格式及编辑器接入尚待 M1/M2 实现。

**安全修改**：模型只能提供候选 `replacement`，用户点击接受时应用还必须再次确认该区间仍等于原先 `quote`，才修改文本并保存新的修订。UI 隐藏 JSON、模型角色、修订号等内部字段。

## 首版明确不做

- 不实现完整 Office / DOCX 排版、分页、复杂表格格式或多人实时协作。
- 不引入讨论串管理、提及通知、复杂审核状态机、多角色权限、统计报表或独立审查历史页面。
- 不在主界面显示 AI 多轮审查过程、模型思维链或长篇评分报告。
- 不为了支持批注而引入数据库。

## 最少验收

1. 选中文本添加批注，关闭重开后选区、批注与正文仍正确。
2. AI 建议只能在用户接受后应用；忽略、撤销、人工修改不丢失。
3. 文档发生变化时，过期 AI 批注不贴错文字，已批准版本不被后台覆盖。
4. 剧本和分镜各验证一次相同的批注与修订交互，不重复制做整套测试报告。

此文档优先级高于任何会让审查体验变成多页面管理系统的旧设计。目标是**Word 的直观操作，AI 的智能批改**，而非复制 Word 的全部功能。
