# TerrySeriesStudio 产品与开发总计划

> 版本：V0.1 规划基线  
> 日期：2026-10-20  
> 状态：已确定方向，尚未开始代码实现  
> 首个验收项目：《异星边境》第一季 EP01  
> 参考仓库：[TerryShotMill](https://github.com/terry-xu-2077/TerryShotMill) / [TerryDirector](https://github.com/terry-xu-2077/TerryDirector)

## 1. 项目使命与成功标准

**把一个人依靠业余时间制作连续剧集的流程，变成能持续运行的 AI 辅助生产系统。**

TerrySeriesStudio 的产品本质是**带 AI 批改与改写能力的文本编辑器**，镜头表格、资产引用、生成和审片只是延伸。它不是“又一个视频生成 UI”，也不是剪辑软件。它解决的是一集剧从文本创作到可交付镜头素材之间的人工重复劳动：剧本反复批改、分镜转换、上下文传递、资产绑定、任务安排、生成失败恢复与局部返工。

### 主要目标

- 以 Project / Season / Episode（项目 / 剧季 / 剧集）组织工作，以 Episode 作为主要生产与交付单位。
- 剧本和分镜脚本均通过**可配置的云端模型 API** 完成创作、独立审查与定向改写。
- 每个阶段的 AI 循环完成后，必须经用户**人工批准**，才能把已批准版本提交到下个生产阶段。
- 视频仅通过**本地 ComfyUI** 调用已有工作流生成，优先复用当前 RTX 3090 环境，后续再扩展可替换的视频生成后端。
- 支持片段间连续性、依赖关系、历史版本、夜间/白天无人值守队列和精确局部重跑。
- 不承担剪辑功能；提供可检视、可筛选、可导出的独立视频素材以及镜头清单。

### 成败如何判断

首个版本不是以控件数量或支持模型数量验收，而是看《异星边境》EP01 能否完成：

**导入设定与现有剧本 → AI 审稿修订 → 人工批准 → AI 分镜与审查修订 → 人工批准 → 自动创建生成任务 → ComfyUI 批量生成 → 人工审片/局部重跑 → 交付独立镜头。**

计划从实际数据评估节省的人工小时。此前每集约 19～32 小时人工投入的估计只作基线；**每集 10～15 小时是待验证的优化目标，不是性能承诺**。GPU 耗时与人工耗时分开统计。

## 2. 范围与已有资产

### 首期生产约束

- 《异星边境》第一季计划 10 集，每集约 2～3 分钟；先用 EP01 验证。
- 角色人物资产已经准备好，应支持直接导入并跨剧集复用；不要默认重新生成角色。**角色档案包括形象图片、声音样本、音色描述和人物文本设定；场景档案包括环境图片、空间/氛围描述与可选环境音**。详见 [ASSET_LIBRARY.md](ASSET_LIBRARY.md)。
- 本地 RTX 3090 实测 H3：15 秒、1080P 约 35 分钟。这个结果作为当前的容量规划基准，需记录后续真实测速。
- 创作者主要工作时间为工作日晚 20:00–24:00、周日约 8 小时；本地 ComfyUI 可在白天或深夜错峰运行。
- 前期专注 Windows 本机与单人创作；后续可拓展团队协作，但不为未验证需求提前增加复杂度。
- 《异星边境》设定内容可从 [OffworldFrontier](https://github.com/terry-xu-2077/OffworldFrontier) 导入项目快照；本软件不直接改写那个创作资料仓库。

### 明确不做

NLE 多轨剪辑、裁切排版、转场、字幕轨、调色、混音、自动成片、剪辑软件兼容工程文件、多用户权限系统、桌面壳优先开发、把推理逻辑重写进本工作台。**非破坏性片段接缝预览与生成上下文拼接属于生成管理，不等于剪辑。**

## 3. 一集剧的四个阶段

### 阶段 A：剧本

输入：故事设定、人物卡、剧集目标、现有剧本或创作要求。

流程：

1. 创建草稿或导入剧本，保留原稿与创作意图。
2. 编剧 Agent 产生候选版本；独立审稿 Agent 检查人物动机、冲突、节奏、设定一致性、时长可行性。
3. 审稿意见采用结构化问题：定位、严重级别、理由、建议；不得只返回“很好”。
4. 改写 Agent 依据问题定向修订，保留用户锁定的段落、对白和设定；之后交给独立审稿 Agent 复查。
5. 默认最多 3 轮审查—修订，可配置，可提前停止。失败、超限或仍有争议时进入待人工处理，不无限自我循环。
6. 用户查看原稿与新稿差异、审查问题和修订历史，可自行修改、添加批注、再次触发 AI。
7. 用户明确批准一个剧本版本，冻结该版本快照，才能进入分镜阶段。

重要：AI 审稿结果是辅助意见，不等同于创作者批准；要允许“保留有意设计的冲突/留白”，避免 AI 把剧本改得平庸。

### 阶段 B：分镜脚本

输入：**已批准**的剧本快照、剧集规则与资产库。

输出：结构化 Scene（场景）和 Shot（镜头），每条包含叙事目的、人物/场景/道具引用、动作与空间关系、预计时长、景别、机位/运动、对白与声音意图、与相邻镜头的叙事关系。

流程：

1. 分镜导演 Agent 自动拆分场景与镜头，明确镜头目的及可见动作，区分“叙事镜头”和“实际生成片段”。
2. 独立分镜审查 Agent 检查视线/轴线/空间一致性、动作承接、角色与道具连续性、节奏、预期时长及模型可生成性。
3. 定向改写并复审，默认最多 3 轮；保存批改原因与版本差异。
4. 用户在可视化分镜列表或卡片中改动顺序、时长、资产和文字描述，并批准某个分镜版本。
5. 系统基于批准的分镜生成 Video Clip Plan：每个镜头可以映射一个或多个生成片段；片段有具体时长、模型提示词与衔接方式。

生成提示词属于**分镜意图的模型适配结果**，不可反向覆盖已批准的分镜。模型切换时可以重新编译提示词，而不需要重新拆整集分镜。

### 阶段 C：本地视频生成

输入：批准的分镜版本与片段计划、已绑定资产、用户选择的 ComfyUI 工作流/Profile。

流程：

1. 把片段字段映射到工作流暴露的显式输入槽位：提示词、资产、时长/帧数、seed、连续性参考等。
2. 提交前校验素材存在、模型能力、输入数量、引用与任务依赖。无效输入应明确报错，不静默丢弃。
3. 生成队列按片段的上下文依赖调度：独立片段可先运行；续接片段须等其依赖的上游结果有效。
4. 通过 ComfyUI HTTP 提交和 WebSocket/历史接口观察进度，持久化状态、重启后恢复对账。
5. 保存每次生成的不变快照：参数、模型/Profile、提示词、输入资产版本、上下文来源、seed、开始/结束时间、错误、输出文件。
6. 审片后用户选择“采用此版本”或“重跑”；历史版本只追加不覆盖。仅重跑受影响片段，而不是重跑整集。
7. 支持“夜间/白天队列”配置：允许提前编排、按依赖执行和失败后受控重试；不要求用户在场，且不主动关闭或重启用户的 ComfyUI 服务。

首期正式生成只验证 **ComfyUI + MiniMax H3**，避免同时适配多个模型导致项目失焦。架构允许之后加入其他 ComfyUI 工作流 Profile。

### 阶段 D：镜头素材交付

- 按剧集与镜头查看已选 Result、时长、分辨率、生成版本、完整状态与缺失项。
- 原始独立视频保留，镜头版本和上下文来源可追溯。
- 导出带稳定 ID 的媒体文件目录与 manifest（JSON/CSV 等通用清单）；不承诺首期输出 Premiere/DaVinci 原生工程。
- 可以做只读相邻片段预览以判断接缝，不提供时间线剪切、转场、混音或自动剪辑功能。
- 明确“已生成”不等于“已审片通过”或“已交付”。

## 4. 核心数据模型与不变量

推荐最小领域模型：

- **Project / Season / Episode**：项目、剧季、剧集，持有创作规范及生产状态。
- **StoryBible / CharacterAsset / LocationAsset / MediaAsset**：世界观与项目级角色/场景档案；图片、声音、文本设定聚合为可复用资产，带稳定 ID、语义标签、主参考图、路径/hash 与版本。角色声音描述独立于音频样本，地点身份独立于分镜 Scene 场次；详见 [资产库设计](ASSET_LIBRARY.md)。
- **ScriptRevision**：剧本文本、AI 审查报告、用户批注、来源、模型、版本、批准状态。
- **StoryboardRevision / Scene / Shot**：由批准剧本派生的结构化分镜与其修订历史。
- **ClipPlan**：一次生成任务的创作意图及与 Shot 的归属关系；1 个 Shot 可含 1..N 个片段。
- **ContextLink**：两个 ClipPlan 之间的连续性类型、固定依赖结果版本及有效性。
- **GenerationJob**：某一次提交到 ComfyUI 的**不可变执行快照**。
- **Result**：媒体文件、校验元数据、质量审核与是否被选为当前采用版本。
- **AuditRun**：一次 AI 创作、审查或修订调用的模型、输入版本、token/费用、输出、错误与耗时。

必须遵守：

1. **叙事顺序不等于生成依赖**：移动卡片不能悄悄修改 ContextLink。
2. **Shot 不等于 ClipPlan**：导演镜头可以拆成多个连续生成片段，但首期 UI 不必暴露复杂层级。
3. **ClipPlan 不等于 Job**：一个片段可反复生成；Job 永远保留当次不可变参数；生成时绑定的图、音频和槽位 manifest 也必须保存在 Job 快照中。
4. **AI 建议不等于用户批准**：进入下一阶段只读取已批准的上游快照。
5. **修改上游时不覆盖下游**：剧本变更后，已生成的分镜/视频标记为“源版本已更新”；用户决定是否重新派生。
6. **资产和结果按 ID/hash 引用**，避免同名素材或绝对路径变化造成静默错绑。
7. **项目、凭据和媒体分开保存**；API Key 不进普通项目导出或生成日志。

状态建议（按阶段分别持有）：Draft → Reviewing → Revising → AwaitingApproval → Approved；失败状态为 Failed / NeedsAttention。视频另有 Queued → Running → Completed / Failed / Cancelled；审片与交付状态单独管理。

## 5. 片段衔接：首版重点

工作台要管理的是**生成连续性**，不是后期剪辑连续性。

### 衔接模式

- **Independent 独立**：只共享叙事/角色信息，不依赖上一片段的画面结果。
- **Tail Reference 尾帧参考**：读取上一个已选结果的尾帧作为视觉参考；建议作为首个优先实现的连续性模式。
- **Continuation 尾帧续接**：采用工作流支持的帧/视频上下文继续动作；不能假设不同模型能力相同。
- **Overlap 重叠生成**：向模型提供重叠的音画/运动上下文，保存重叠区及语义参数。是否裁掉重复帧由下游后期决定，不隐式修改原始视频。

Capability/Profile 负责声明模式及限制，不支持时在 UI 中禁用并解释原因；禁止静默从续接降级到独立模式。

### 依赖与局部返工

案例：A-V3 → B-V2 → C-V1。

- B 的 Job 必须记录它引用的是 **A-V3**，而不是浮动的“A 最新版本”。
- A 被批准为 V4 时，B 及通过依赖链间接受影响的 C 显示 **Context Stale**。
- 用户可以保留旧链，也可以选择从 B 开始重新生成；系统不得自动删除 B/C 的历史结果。
- 上游没有成功媒体时，下游明确进入 Blocked，不伪造尾帧；支持从已有视频资产建立实体上下文起点。
- 断点继续需验证已完成媒体文件真实存在、规格有效，不能只凭数据库状态认为成功。

## 6. 技术架构与复用策略

### 模块边界

**Frontend（React + TypeScript）**
- 单一轻量编辑工作台，主要导航：剧本、分镜、生成；资产可在需要时打开，不强制占用常驻侧栏。
- 剧本文字及 diff/批注、镜头卡片与 Inspector、只读片段接缝预览、任务运行中心。
- 禁止重复维护一套独立于后端的创作真相。

**Core Service（Node.js + TypeScript；文件驱动，不使用 SQLite）**
- 用普通工程文件管理编辑内容、版本、批准状态、片段上下文依赖与任务回执。首期以 `project.json` 为工程入口，剧本为 Markdown、分镜及必要记录为 JSON，图片/声音/视频仍存普通文件；只在实际需要时才拆分更多文件。
- 文件保存采用临时文件 + 原子替换；保留最小备份/恢复机制；编辑时延迟自动保存。进程重启时用文件中的 ComfyUI prompt_id 和其历史记录对账，不靠内存猜测任务是否完成。
- 写操作具备版本冲突检查；提交、重试支持幂等键；刷新浏览器和服务重启不能丢任务。
- 只在此层判定“能否进入下一阶段”，不能由前端按钮或 AI 模型直接决定。
- **本地常驻 Node.js 仅负责必需的执行能力**：浏览器关闭后保存执行结果、排有依赖的生成片段、对账 ComfyUI 状态，云端 API Key 不能暴露给浏览器。不要构建通用工作流引擎、数据库模型层或复杂的微服务架构。
- 本地默认仅监听 `127.0.0.1`；若未来允许手机或远程访问，须另做身份验证、来源限制与安全配置。

**AI Provider Adapter**
- Node.js 服务端调用云端 API，支持可配置端点、Key、模型、超时及参数，首选 OpenAI-compatible 接口，厂商差异通过 Adapter 隔离。
- 同一 Provider 可配置编剧、审查、分镜等多个角色，**逻辑角色分离不意味着必须调用不同模型**。
- 输入按项目设定 + 当前场景/上下文 + 规则快照构成；响应首先做 schema 校验，再进入内容审查，记录每次调用的耗时与用量。

**ComfyUI Adapter**
- ComfyUI 是独立的 Python/GPU 生成引擎，使用其**现有 Python 环境**；TerrySeriesStudio 不运行第二套 Python，也不复制模型、不接管 ComfyUI 的启动/关闭。通过 HTTP `/prompt`、`/history`、`/queue` 和 WebSocket `/ws` 等接口调用已有工作流。
- 工作流输入槽位明确标记/映射，支持导入 Profile、检查参数和实际媒体是否送达。
- 负责队列、状态对账、生成输入与结果路径，处理上下文媒体引用；不自行实现 H3 采样或视频后期。

### 两个旧仓库的使用办法

| 来源 | 值得参考/复用 | 不直接照搬 |

## 7. 开发阶段与验收

### M0 · 架构骨架与可运行 Demo

交付：本地 Node.js 服务与前端启动、可打开与保存的普通工程文件、剧本/分镜文本编辑器、角色/场景最小资产资料（图片、音频、描述）、Mock AI 和 Mock ComfyUI，以及三个创作阶段的轻量导航。UI 优先使用旧 ShotMill 分镜表已确认的布局、编辑和媒体展示体验，避免重新堆叠一个生产管理平台。

验收：Windows 本地可打开 EP01 的模拟项目；能导入已有角色图片、声音样本与人物文本，并创建场景资产；跨阶段数据完整持久化，重启后状态不丢；没有实际模型调用也能演示完整主流程。

### M1 · 剧本 AI 创作与审核闭环

交付：文本编辑、可配置云端 API、生成/独立审查/定向改写、次数上限、diff/问题清单、版本与人工批准，以及角色/场景设定作为可追溯的 AI 上下文。

验收：导入一份 EP01 剧本后可以多轮自动批改；用户保留手动修改，批准指定版本；未批准版本无法触发正式分镜派生；每次 API 调用可追溯。

### M2 · 分镜 AI 闭环与生成计划

交付：批准剧本 → Scene/Shot；可视化镜头卡片、角色/场景稳定 ID 绑定及所选参考媒体、导演审查与定向改写、分镜批准、ClipPlan/ContextLink、面向 H3 的提示词编译。

验收：一场戏自动产生可编辑且结构化的分镜；修改剧本能提示分镜来源过期；批准分镜后生成的 ClipPlan 带稳定 ID、时长、Prompt 和资产引用。

### M3 · ComfyUI 视频生成与衔接

交付：ComfyUI 工作流 Profile、资产参考图片/声音与提示词编号统一的 AssetBindingManifest、输入映射与验证、顺序/依赖队列、运行恢复、视频入库、独立/尾帧参考、版本选择、局部重跑和 Context Stale。

验收：用 RTX 3090 的真实 H3 工作流运行至少三条有依赖的片段；中途服务重启后能恢复状态；重跑第二条不覆盖第一条或历史视频；上游换版时准确提示下游过期。

**尾帧续接与重叠**根据当前 ComfyUI 工作流能力在 M3 后续增量支持，但数据结构从一开始预留，不以未实现的模式阻碍首条闭环。

### M4 · EP01 全集试产

交付：完整一集的场景/镜头任务与独立视频素材包、审片与交付清单、失败恢复与手动返工流、生产统计。

验收：从 EP01 剧本到可供 NLE 后期使用的媒体素材包，全程无需手动转抄剧本、分镜或生成任务；可以按镜头定位错误、批改和重跑；数据记录能解释人工时间、云端 API 费用、GPU 占用与返工率。

### M5 · 根据第一集数据优化（不提前开发）

只在真实试产暴露瓶颈之后考虑：跨集资产与角色记忆增强、队列优先级、夜间批处理安全策略、更多工作流/模型、自动发现失效镜头、远程状态查看等。

## 8. 第一版开发纪律

1. **编辑器优先，先纵向打通**：首先让 EP01 剧本、分镜、资产文本能够可靠编辑并保存，再接 AI 和视频生成，不先做大量设置页、管理控制台或新 UI 装饰。
2. **只保留高价值的少量验收**：文本保存重开不丢、AI 不静默覆盖人工内容、片段衔接和重跑不串错、不覆盖历史文件。重要接口用 Mock 快速验证，必要阶段用少量真实 API/ComfyUI 样例确认，不扩建测试报告体系。
3. **一个字段只保存一份权威状态**：后端 Core 是真相来源，前端和 ComfyUI 只做展示与执行。
4. **明确区分系统故障、AI 质量意见和人工审批**：质量建议不会被当成运行失败，AI 审查也不能伪装成用户通过。
5. **所有昂贵工作都可追溯且可恢复**：API 调用记录用量，视频保存不可变任务快照、媒体路径与检查结果。
6. **不要不必要地重新生成**：改写只定向改动相关内容，GPU 重跑只追踪受影响片段及其可选下游。
7. **不编造成功**：模型或工作流无能力、媒体缺失、未验证的运行必须准确展示为不可用/待验证。
8. **保护原项目**：旧仓库和《异星边境》设定仓库只作参考与导入来源，未经明确要求不对其做自动修改。

## 9. 当前下一步

**从 M0 开始**，先直接参考旧 ShotMill 的分镜表交互，建立工程文件读写、基础文本编辑和必要的状态字段；然后按 M1 → M2 → M3 顺序实现。首次真实 ComfyUI 验收范围先控制在 EP01 的 1 场戏、3 个连续片段，再扩展为整集。

此文件是产品范围和开发顺序的起始基线；具体实现可迭代，但涉及产品边界、审批关卡、数据真相来源和非剪辑定位的变更应先更新本计划。
